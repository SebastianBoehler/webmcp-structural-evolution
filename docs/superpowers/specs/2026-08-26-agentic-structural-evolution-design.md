# Agentic Structural Evolution Workbench

Date: 2026-08-26

Status: Product architecture approved in chat

Product name: This document uses a descriptive label; the entrant will choose the public name.

## Product thesis

Build an open, local-first web application where a person and an agent turn a real component inventory into a printable, structurally optimized assembly body. The first hero workflow generates a drone motor arm around actual mounting interfaces, masses, keep-outs, materials, printer constraints, and load cases.

The challenge release is a focused vertical slice and does not yet claim certified engineering analysis. The product ambition is broader: become an open, agent-native replacement for substantial CAD/CAE workflows by making geometry, simulation, optimization, manufacturing constraints, and verification one inspectable system. Its initial differentiator is a complete loop:

1. Inventory and target outcome define the available assembly.
2. Components compile into explicit geometry, loads, constraints, and manufacturing limits.
3. A 3D WebGPU topology optimizer creates reproducible candidates.
4. The person and agent inspect the same live state, compare evidence, and redirect the search.
5. A selected candidate is independently re-analysed before export.
6. The application exports a watertight STL and an evidence report.

## Audience and business wedge

The initial user is a small drone, robotics, or hardware team that knows which components and fabrication equipment it owns but lacks an accessible generative-design workflow. The immediate value is faster concept exploration with transparent assumptions. The long-term goal is to replace increasingly large portions of closed professional CAD/CAE stacks, including validated analysis and qualification workflows, rather than remain a visualization or pre-design companion.

Reaching that goal requires solver verification, experimental validation, standards-aware reports, manufacturing feedback, exact CAD interchange, and documented assurance cases. Those capabilities are roadmap obligations, not claims made by the challenge release.

The component library creates a durable expansion path: personal inventories, team catalogs, supplier data, parametric interfaces, CAD exchange, more manufacturing processes, and additional physics can follow after the challenge without changing the core assembly contract.

## Challenge fit

The official challenge evaluates four equally weighted dimensions:

- **WebMCP leverage:** structured tools let the agent inspect exact live assembly state, compile constraints, run variants, and compare evidence without guessing through a visual editor.
- **Execution:** the project delivers one coherent path from owned components to an exportable artifact, not only a solver demonstration.
- **Potential impact:** it addresses an expensive and specialized workflow for a specific hardware audience while remaining open and browser-native.
- **Creativity and ambition:** it combines original 3D browser compute, agent-human co-steering, inventory-aware design, and visible validation.

## Core domain model

All state-changing actions create immutable revisions. Identifiers refer to exact revisions rather than display names.

### ComponentDefinition

- Stable ID, revision, category, manufacturer, part number, and source provenance.
- Mass and center of mass.
- Primitive or curated mesh envelope.
- Mount interfaces with position, orientation, diameter, and fastener type.
- Keep-out, access, cable, and cooling volumes.
- Load contributions and allowed orientations.

### InventoryItem

- Component revision and owned quantity.
- Optional user label and notes.
- Availability status; no invented substitute when stock is insufficient.

### AssemblySpec

- Exact component instances and transforms.
- Target envelope and preserved mounting geometry.
- Obstacle and access volumes.
- Missing, incompatible, or ambiguous components.
- Derived bill of materials.

### StudySpec

- Assembly revision.
- Design region and voxel resolution.
- Material profile and manufacturing profile.
- One or more named load cases.
- Fixed regions, force vectors, objectives, and hard limits.
- Deterministic seed and solver revision.

### OptimizationRun

- Immutable study snapshot hash and parent run.
- Solver/backend versions and device capability summary.
- Iteration history, timings, convergence, warnings, and terminal status.
- Candidate density field, extracted surface revision, and metrics.

### ValidationReceipt

- Exact candidate and study hashes.
- Re-analysis mesh/resolution and numerical tolerances.
- CPU/GPU comparison where applicable.
- Mass, compliance, displacement, stress estimate, and mesh-integrity checks.
- Explicit passed, failed, or not-evaluated status for every check.

## Component and inventory experience

The first release includes a small, attributed catalog of real or clearly generic drone components plus structured custom parts.

A custom part accepts dimensions or a primitive envelope, mass, mount anchors, keep-outs, stock count, and provenance. Arbitrary STEP/STL interpretation and automatic interface extraction are excluded from the first release.

The application supports two reciprocal questions:

- Which complete assemblies can be built from this inventory?
- Which inventory items are required or missing for this target assembly?

An assembly is never labelled buildable when quantities, mount compatibility, or required metadata are unresolved.

## Optimization architecture

### Production solver

- Direct WebGPU compute using WGSL kernels with TypeScript orchestration.
- Regular 3D hexahedral voxel grid and linear isotropic elasticity.
- Matrix-free preconditioned conjugate-gradient displacement solve.
- SIMP density interpolation, sensitivity analysis, spatial filtering, and optimality-criteria updates.
- Multiple load cases combined by explicit weights.
- Deterministic initialization and stable reduction strategy where browser support permits.
- Compute runs asynchronously so the viewport and cancel controls remain responsive.

Initial performance target: complete the hero study at approximately 48 × 24 × 24 elements in at most 60 seconds on the target Apple Silicon development machine while keeping interactive camera motion smooth. This is a benchmark target, not a submission claim until reproduced in the deployed challenge browser.

### Independent reference

A small Rust solver compiled to WebAssembly implements the same element formulation and objective for low-resolution canonical cases. It is an oracle for correctness, not a fallback production solver.

The GPU implementation must pass:

- element-matrix and symmetry checks;
- analytical cantilever displacement within 5% of the Euler-Bernoulli fixture at its locked reference resolution;
- MBB-beam compliance within 1% of its committed baseline and a maximum mirrored-density difference of `0.02`;
- deterministic replay on the same supported device path;
- CPU/GPU relative L2 displacement agreement within `5e-4` and compliance agreement within `1e-3` on identical f32 small-grid fixtures;
- monotonic sanity checks when loads, stiffness, or volume fraction change.

The conjugate-gradient solve must reach a relative residual of `1e-5` or report non-convergence. Failed checks remain visible and block a “validated” receipt. Baselines may change only through an explicitly reviewed fixture revision, never as part of performance tuning.

### Surface extraction and export

1. Threshold the converged density field.
2. Extract a surface with marching cubes.
3. Apply only bounded, deterministic cleanup.
4. Check manifoldness, watertightness, normals, connected components, and minimum-feature heuristics.
5. Revoxelize or remesh the extracted result and run post-optimization analysis.
6. Export binary STL only when required integrity checks pass.

“Printable” means a watertight STL that passes the documented geometric and minimum-feature heuristics. It does not guarantee printer settings, material behavior, fatigue life, regulatory compliance, or safe flight.

## Human-agent creative loop

The collaboration model is not a chat panel attached to CAD. The shared artifact is the conversation: selections, constraints, branches, computed evidence, and decisions remain spatially and causally linked in the workbench.

1. **Point:** the person selects, paints, or locks a semantic region in the 3D view. The selection has a stable region ID and an accessible DOM summary, so the agent reads the exact same object without inferring it from pixels.
2. **Translate:** the agent converts intent into a bounded constraint handshake: proposed preserve/keep-out regions, load case, objective, assumptions, and expected trade-off. Proposed facts and measured facts are visually distinct.
3. **Fork:** an agent action creates a reversible experiment branch from an exact parent revision. It never mutates the accepted branch invisibly. The card records the hypothesis, changed constraints, parent, predicted effect, and tool receipt.
4. **Probe:** local compute attaches measured results and validation status to that branch. A failed or counterintuitive result remains as evidence rather than disappearing.
5. **Compare:** the person and agent inspect a small counterfactual set—such as lighter versus stiffer, or protected cable path versus unrestricted path—with synchronized metric deltas and viewport highlights.
6. **Interrupt:** the person can lock a mount, change inventory, stop a run, or reject an assumption at any point. The current plan becomes stale visibly; the agent receives the new revision and valid next actions without the person restating the project.
7. **Promote:** only the person can promote a candidate into the accepted design lineage and authorize final re-analysis/export.

This creates several novel interaction primitives:

- **Constraint handshake:** natural language becomes inspectable engineering state before expensive compute.
- **Spatial deixis:** “keep this clear” resolves to exact geometry and survives later turns.
- **Hypothesis versus evidence:** the agent states what it expects before the solver records what happened.
- **Branching dialogue:** alternatives are durable design branches, not ephemeral chat suggestions.
- **Evidence-linked explanation:** every recommendation cites exact revisions, runs, metric deltas, warnings, and receipts; selecting a claim highlights the supporting geometry.
- **Productive disagreement:** the agent can surface an infeasible or dominated request and propose the smallest relaxation, while the person retains authority.
- **In-situ alternatives:** selecting one arm, leg, joint, rib, or other semantic part lets the agent stage several valid local configurations around that exact anchor. The accepted part remains solid while alternatives render as distinct ghost bodies in the same coordinate frame.

In-situ alternatives have three rendering modes:

- **Overlay:** alternatives occupy their true assembly coordinates, using bounded opacity/dither and clear branch colors to reveal local material and clearance deltas.
- **Peel:** alternatives fan a small distance away from the selected anchor with connector guides, preserving orientation and making silhouettes readable without losing assembly context.
- **Audition:** one alternative temporarily replaces the selected part in the full assembly so collisions, keep-outs, interfaces, and load paths can be inspected before any promotion.

Hovering or focusing an alternative highlights only its local geometric delta and its linked experiment card. Selecting it synchronizes the branch revision, hypothesis, measured metrics, warnings, and viewport. A person can ask the agent to combine explicit features from exact branches—for example, “use this cable channel with option C's rib”—which creates another staged branch instead of destructively merging meshes. Alternatives are capped to a small comparison set, share exact anchors/transforms, and always have equivalent semantic DOM controls and metric summaries outside the canvas.

The judge-mode foundation uses the same pattern at smaller scale: inspect an exact study, stage a bounded experiment, run verified compute, compare branches, intervene through a visible lock/selection, and explicitly promote the evidence to the active branch. It must never present a predicted effect as a solver result.

## WebMCP tool contract

Use the imperative `document.modelContext.registerTool` API. Register only tools valid for the current page state and dispose registrations with abort signals when state changes.

1. `inspect_design_context`: return the selected project, active semantic selection/locks, inventory summary, accepted and staged branch revisions, study status, stale-plan status, and available next actions. Read-only.
2. `query_buildable_assemblies`: evaluate inventory against shipped assembly templates and return exact missing or incompatible items. Read-only.
3. `configure_assembly`: stage a reversible assembly branch from explicit component revisions, quantities, transforms, and a stated hypothesis.
4. `configure_study`: stage a study branch with bounded material, manufacturing, load, objective, resolution inputs, assumptions, and predicted trade-offs.
5. `run_optimization_variant`: launch a reversible local run from an exact staged study or parent-run revision; measured output never overwrites the prediction.
6. `compare_candidates`: return normalized measured deltas, validation status, constraint violations, and trade-offs for exact run IDs. Read-only.
7. `stage_export`: prepare an STL/report bundle and show it in the UI; the person performs the final download.

Although seven tools are defined, dynamic registration limits each state to the smallest useful set. Inputs use narrow JSON Schemas with no arbitrary code, HTML, file paths, or remote URLs. Tool results contain structured facts and bounded human-readable summaries. Existing domain validation is shared by the UI and tools.

Every invocation produces a visible receipt with tool name, validated inputs, affected revision, result, duration, and error. Consequential acceptance and download remain explicit human actions.

Agent proposals and measurements use separate fields and visual treatments. The agent may stage branches and run bounded local experiments, but branch promotion, relaxation of a human lock, and export are not agent-callable actions.

## Security and trust boundaries

- Website tool definitions and outputs are treated as untrusted content, consistent with [OpenAI Site tools guidance](https://learn.chatgpt.com/docs/webmcp) and the [WebMCP security considerations](https://webmachinelearning.github.io/webmcp/#security-and-privacy-considerations).
- The agent cannot execute user-authored code, fetch arbitrary URLs, or mutate hidden state.
- UI and WebMCP paths call the same validation and domain services.
- Component provenance text is data, never instructions.
- Local inventory remains in the browser unless the person explicitly exports it.
- Run cancellation, numerical failure, unsupported WebGPU, and invalid geometry fail clearly.

## Lessons carried forward from Cobia

- Preserve exact identity: component revision, mount, unit, material, solver revision, and candidate hash are never normalized into convenient but different entities.
- Bind generation to a snapshot: every optimization run starts from an immutable study and produces replayable evidence.
- Fail closed: an infeasible, numerically failed, or unverified candidate is never promoted merely to show a result.
- Separate product truth from presentation truth: deployed code is insufficient until judge-visible evidence reflects the actual capability.
- Use real recordings as canonical evidence: presentation media may frame execution but must never fabricate it.
- Distinguish declared capability from proven outcome: a tool registration, completed kernel, or pretty mesh does not establish structural validity.

## Explicit exclusions for the challenge release

- Universal rigid-body, fluid, cloth, molecular, or atom-level physics.
- Arbitrary CAD import and automatic feature/interface inference.
- STEP/B-rep export.
- Certified design, fatigue, fracture, thermal, CFD, or nonlinear material analysis.
- Cloud solver, accounts, collaboration backend, billing, marketplace, or ERP inventory.
- General scene editor, plugin system, arbitrary scripting, or generated shader editor.
- Silent CPU, server, or saved-result fallback when WebGPU fails.

## Acceptance gates

### Feasibility gate

- WebGPU compute and WebMCP both work on the deployed URL in ChatGPT's in-app browser.
- The hero grid completes within the measured demo budget and remains visually responsive.
- Small GPU results agree with the Rust/Wasm reference within fixed tolerances.
- The extracted hero mesh is watertight and passes post-extraction re-analysis.

### Product gate

- A first-time visitor can identify the user, problem, outcome, and differentiator within 10 seconds.
- The hero flow works without authentication or manual data entry.
- A custom component changes assembly compatibility and the resulting study.
- Human intervention changes the agent's next action without restating the whole project.
- A judge can point to or lock exact geometry, see the agent's typed interpretation before compute, and distinguish its prediction from measured evidence.
- Two counterfactual branches remain inspectable with parentage, constraint deltas, and linked viewport evidence.
- A selected part can display multiple anchored alternative configurations in overlay, peel, and audition modes without losing the surrounding assembly context.
- An accepted candidate yields a real STL, BOM, assumptions, and validation report.

### WebMCP gate

- Fixed journey evals cover tool discovery, selection, argument validity, chaining, state changes, and failures.
- No overlapping tool descriptions or tools registered outside valid states.
- Exact revisions and visible receipts connect every agent action to UI state.
- Export remains human-confirmed.

### Submission gate

- Public repository under Apache-2.0 with a visible licence, full source, assets, setup, architecture, and attribution.
- Live URL verified in both supported judging paths where available.
- Video remains below three minutes and shows actual product behavior with audio.
- README and screenshots independently establish all four judging dimensions.
- Submitted repository and live deployment remain frozen throughout judging, as directed by the challenge FAQ.

The release succeeds when a judge can open one page, understand the outcome immediately, watch a human and agent jointly create and redirect a genuine 3D optimization, inspect evidence that prevents a false win, and download a real STL/report bundle—all without confusing the project for a NASA product or a certified engineering tool.
